## 0. عن المستند ده

ده اختصار مقصود لوثيقة الـ SRS الكاملة، بيركّز على **أقل مجموعة مزايا** لازمة عشان نطلق سوق صيانة سيارات ثنائي (B2C + B2B) شغّال في **مدينة واحدة**. كل ميزة بَرّه الحلقة الأساسية (متتبّع الصيانة، التذكيرات، التقييمات، التحليلات… إلخ) **مؤجَّلة** ومذكورة صراحةً في القسم 7.

أرقام المتطلبات (FR-x.x) **متطابقة** مع الوثيقة الكاملة عشان التتبّع يفضل سهل بين النسختين.

## 1. مقدّمة

### 1.1 الغرض
نُعرّف بدقّة المزايا والمتطلبات الوظيفية وغير الوظيفية للإصدار الأول (MVP) من منصّة «أسطى»، بحيث يقدر فريق التطوير يبني ويطلق نواة المنتج من غير تشتّت في مزايا المراحل اللاحقة.

### 1.2 نطاق الـ MVP

**داخل النطاق (In-Scope):**
- تطبيق العميل (B2C) وتطبيق الأعمال (B2B) على iOS/Android.
- كونسول عمليات للأدمن (ويب بسيط أو تطبيق مبسّط — مفتوح للتنفيذ).
- توثيق بالموبايل (OTP) + إدارة أساسية للعربيات.
- اكتشاف المراكز على الخريطة + فلاتر + بحث.
- ملفات المراكز وخدماتها.
- حلقة حجز كاملة: اختيار خدمة ← ميعاد ← تأكيد ← دفع.
- تأهيل المراكز (B2B) برفع المستندات + التحقّق.
- كتالوج وأسعار + قبول/رفض الحجوزات + لوحة تحكّم حيّة (B2B).
- طابور تحقّق + حلّ نزاعات يدوي (الأدمن).
- لغتين (إنجليزي افتراضي + عربي مصري) بتخطيط RTL.

**خارج النطاق (Out-of-Scope للـ MVP):** متتبّع الصيانة، التذكيرات الذكية، متتبّع المصاريف/الوقود، التقييمات والردود، CRM، التحليلات المتقدّمة، الباقات والاشتراكات، التحويلات/العمولات الآلية، الطوارئ، الذكاء الاصطناعي، سوق قطع الغيار، والتوسّع لأكتر من مدينة. (التفاصيل في القسم 7.)

### 1.3 مصطلحات أساسية
- **B2C:** تطبيق العميل صاحب العربية.
- **B2B:** تطبيق مركز الخدمة.
- **Slot:** ميعاد حجز متاح عند المركز.
- **Hold:** حجز مؤقّت للميعاد لمدة 10 دقائق لحد ما الدفع يكتمل.
- **Verification:** تحقّق الأدمن من مستندات المركز قبل ظهوره للعملاء.

## 2. الوصف العام

### 2.1 منظور المنتج — حلقة السوق
المنتج سوق ثنائي محوره **الاكتشاف بالخريطة (Map-first)**. الحلقة الأساسية:

```
العميل يكتشف مركز على الخريطة ← يختار خدمة وميعاد ← يدفع ويأكّد الحجز
        ↓                                                   ↑
المركز يستقبل الحجز لحظيًا ← يقبل/يرفض ← ينفّذ ويحدّث الحالة ──┘
        ↑
الأدمن يتحقّق من المركز قبل ما يظهر في نتائج الخريطة
```

### 2.2 المستخدمون والأدوار
| الدور | الوصف | التطبيق |
|---|---|---|
| العميل (Customer) | صاحب عربية بيدوّر على خدمة ويحجز | B2C |
| صاحب المركز (Shop Owner) | بيدير ملف المركز والكتالوج والحجوزات | B2B |
| الميكانيكي (Mechanic) | بيتسند له الحجز وبينفّذه | B2B |
| الأدمن (Admin) | بيتحقّق من المراكز ويحلّ النزاعات | كونسول العمليات |

### 2.3 القيود والافتراضات
- **مدينة واحدة** في الـ MVP، عملة **الجنيه المصري (EGP)**.
- منصّات: **iOS 14+** و **Android 8.0+ (API 26+)**.
- اعتماد على خدمات سحابية مُدارة مع **تجريدات** تقلّل الارتباط بمزوّد واحد.
- مزوّدو الطرف الثالث (خرائط، دفع، SMS، إشعارات) متاحين وموثوقين.

## 4. المتطلبات غير الوظيفية (مختصرة)

| المجال | المتطلب |
|---|---|
| **الأداء** | استعلام «المراكز القريبة» p95 < 200ms (بـ 50–500 مركز)؛ تحميل الخريطة < ثانيتين؛ زمن استجابة عام p95 < 500ms تحت 100+ مستخدم متزامن. |
| **الأمان** | توثيق بتوكِنات قصيرة العمر + تخزين آمن على الجهاز؛ RBAC + تصريح لكل سجلّ؛ TLS 1.3؛ تشفير كلمات السر؛ **عدم تخزين بيانات البطاقة** (توكنة عبر بوابة الدفع)؛ روابط موقّعة للملفات الخاصة. |
| **الموثوقية** | إتاحة ≥ 99.5%؛ منع الحجز المزدوج (Hold + قفل تزامن)؛ عمليات الدفع Idempotent. |
| **التوطين** | إنجليزي (افتراضي) + عربي مصري؛ تخطيط RTL كامل؛ تواريخ/أرقام حسب اللغة؛ عملة EGP؛ استيعاب تمدّد النص العربي (~30%). |
| **الوصولية** | أحجام لمس مناسبة، تباين ألوان كافٍ، دعم قارئ الشاشة للعناصر الأساسية. |
| **قابلية الصيانة** | معماريّة طبقية/مَهمّية (modular) تفصل منطق المجال عن الواجهة والبنية التحتية. |

## 5. نموذج البيانات الأساسي

كيانات الـ MVP (7 كيانات أساسية):

| الكيان | ملاحظات |
|---|---|
| **User** | الدور (customer/shop_owner/mechanic/admin)، اللغة المفضّلة. |
| **ServiceCenter** | موقع جغرافي `POINT` + فهرس مكاني، ساعات العمل، `is_verified`. |
| **Service** | تابعة للمركز: اسم، سعر، مدّة. |
| **Vehicle** | تابعة للعميل: ماركة/موديل/سنة، عربية أساسية، حذف ناعم. |
| **Booking** | حالة: `pending→confirmed→in_progress→completed→cancelled`؛ `hold_expires_at` (10 دقائق). |
| **Payment** | مرتبطة بحجز؛ بدون تخزين بيانات بطاقة. |
| **Notification** | إشعارات دورة حياة الحجز/التحقّق. |

**ملاحظة تقنية محايدة:** يتطلّب النموذج **قاعدة بيانات علائقية بدعم استعلامات جغرافية (Geospatial/PostGIS-compatible)** و**قناة لحظية (Realtime/WebSocket)** لتحديث لوحة الأعمال — من غير التزام بمزوّد بعينه.

**العلاقات:** المستخدم ← عربيات (1:N)؛ المستخدم ← مركز (1:1 لصاحب المركز)؛ المركز ← خدمات (1:N)؛ الحجز يربط (عميل، عربية، مركز، خدمة، ميعاد)؛ الحجز ← دفعة (1:1).

## 6. حالات الاستخدام الأساسية

**UC1 — العميل بيحجز خدمة:** يفتح الخريطة ← يشوف المراكز القريبة ← يطبّق فلاتر ← يدخل ملف مركز ← يختار خدمة وميعاد ← يتعمل **Hold 10 دقائق** ← يدفع ← يتأكّد الحجز ويوصل إشعار للطرفين.

**UC2 — تأهيل مركز خدمة:** صاحب المركز يسجّل ← يرفع المستندات ← يجهّز كتالوج مبدئي ← يدخل حالة «معلّق» لحد قرار الأدمن.

**UC3 — المركز بيستقبل ويكمّل حجز:** يوصل إشعار لحظي ← يقبل/يرفض ← (لو قبل) يسند ميكانيكي ويحدّث الحالة خطوة بخطوة ← العميل بيتابع التحديثات.

**UC5 — الأدمن بيتحقّق من مركز:** يفتح طابور التحقّق ← يراجع المستندات ← يقبل/يرفض/يطلب معلومات ← المركز المقبول يظهر في نتائج الخريطة.

## 8. خطة التسليم (مختصرة)

الهدف: سوق ثنائي شغّال في **مدينة واحدة**. مايلستونات مرتّبة بالمخاطرة:

1. **الإعداد:** هيكل المشروع، قاعدة البيانات + الدعم الجغرافي، الأدوار، خطّ CI أساسي.
2. **التوثيق والمستخدمون (FR-1):** تسجيل/OTP/دخول/خروج، RBAC، الملف الشخصي واللغة.
3. **الاكتشاف (FR-2, FR-3) ← أعلى مخاطرة:** استعلام المراكز القريبة + الفلاتر، ملف المركز وخدماته ومواعيده.
4. **الحجز والدفع (FR-4) ← أعلى مخاطرة:** آلة حالة الحجز + Hold 10 دقائق + اختبار التزامن، الدفع والاسترداد، قبول/رفض B2B.
5. **اللحظي (FR-4.6, FR-10):** قناة لحظية + بثّ أحداث الحجز للوحة الأعمال.
6. **تأهيل + كتالوج (FR-9, FR-11) + العربيات (FR-5).**
7. **كونسول الأدمن (FR-16/17):** طابور التحقّق، حلّ نزاعات يدوي.
8. **الإشعارات والتقوية (FR-19, NFRs):** Push لدورة حياة الحجز، حدود معدّل، تدقيق، اختبار حِمل.

> **الفريق المقترح:** ~5 مهندسين، إطار العميل **Flutter** للتطبيقين (متّفق عليه في النسختين). الباك-إند يُحسَم لاحقًا بدون تغيير المزايا أعلاه.

## 9. معايير القبول (تعريف «تمّ» للـ MVP)

- اختبارات الوظائف الأساسية خضراء، وتحليل ساكن نظيف.
- **الاكتشاف:** استعلام المراكز القريبة p95 < 200ms.
- **الحجز:** مفيش حجز مزدوج تحت التزامن؛ الـ Hold بيتحرّر بعد 10 دقائق لو الدفع ما اكتملش؛ عمليات الدفع Idempotent.
- **اللحظي:** حدث الحجز يوصل للوحة الأعمال المشتركة في القناة.
- **التحقّق:** مركز يتقبل من الأدمن ← يظهر فورًا في نتائج «المراكز القريبة».
- **التوطين:** التطبيق شغّال بالكامل عربي (RTL) وإنجليزي.

## 11. الأسئلة المفتوحة
1. الباك-إند النهائي للـ MVP: نكمّل بالخيار اللي في `osta_backend_plan.md` (Laravel + Filament) ولا حلّ مُدار آخر؟ (القرار ما بيغيّرش المزايا أعلاه.)
2. كونسول الأدمن: لوحة ويب مبسّطة ولا تطبيق Flutter مبسّط؟
3. مزوّدو الخرائط والدفع والـ SMS المعتمدين في المدينة المستهدفة.
4. سياسة الإلغاء والاسترداد التفصيلية في الإطلاق.
